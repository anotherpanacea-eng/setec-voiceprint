# SVP Surface Harness — a forward-only CLI/envelope/report harness, plus a structurally-verified path to adopting it in guard-protected modules

**Status:** Draft (proposal — independent adversarial review required before any build) · **Date:** 2026-08-06 · **Repo:** `setec-voiceprint`

**Provenance:** `specs/svp-packaging-conversion.md` §3 explicitly withdrew `setec.surfaces.harness` and all surface-boilerplate consolidation from its own scope: "Any future shared CLI/envelope/report harness is a separate specification and independent review after the relocation settles; it cannot enter as a packaging cleanup." This is that separate specification. It does not reopen packaging's P0–P5 scope and proposes no change to `plugins/setec-voiceprint/scripts/setec/`'s layout, the not-yet-built layering checker's rules, or `packaging_move_map.json`'s existing schema. It is independently sequenced (see §9) and, on the evidence below, does not need to wait for packaging's P4.

**This draft went through two scope revisions during authoring, both recorded here because the reasoning is load-bearing for review:** an initial pass scoped a guard amendment; a strategic re-adjudication cut it entirely to a forward-only ratchet, reasoning that `tools/check_claim_license_guard.py`'s lack of judgment is its strength and any amendment is attack surface; the owner then overruled that cut, on the grounds that a breaking `ClaimLicense` contract change (schema 2.0, a new required field, a changed `reason_category` taxonomy) is expected within roughly a year, will fan out to all guard-protected call sites regardless of whether this spec exists, and should get calm design and adversarial review now rather than a rushed amendment under deadline pressure later. That is the condition under which this document should be re-read if it sits unbuilt: if a breaking `ClaimLicense`-contract change becomes concretely scheduled, the guard amendment in §6 stops being optional infrastructure and becomes the difference between a reviewed mechanism and an ad hoc one.

## 0. Executive summary

1. **Mandatory forward-only ratchet** (§5): every *new* top-level surface must use the harness's CLI/envelope/report/`_emit` helpers; a new checker blocks a new hand-rolled copy of that scaffolding. This is the durable win — 54 new `capabilities.d` entries landed in the 60 days before this spec was drafted, so the growth channel this closes is active, not hypothetical. It touches zero existing files and cannot conflict with the claim-license guard, because it only inspects paths absent from the merge base.
2. **Optional adoption of the 30 modules already outside the guard's protected closure** (§7): real, but small. Only 4 of those 30 (4,255 LOC) actually build a `output_schema.build_output`/`build_error_output` envelope at all — the other 26 are acquisition/utility scripts with no envelope to standardize. Net yield: on the order of 300–500 LOC. Worth doing because it is free (no guard interaction whatsoever), not because it is the point.
3. **A guard amendment authorizing adoption inside the protected closure** (§6): the hard part, designed to be attacked. It never compares against anything a PR can author — the "before" side is always re-derived from the merge base by CI, exactly as `tools/check_claim_license_guard.py` does today. It never substitutes text by a committed old/new string pair (that exact shape was tried once in this repo's history and is pinned as a regression test — see §6.2). It authorizes only a small, closed, *code*-defined registry of structural rewrites, each of which is proven, per adoption, to (a) reconstruct the merge-base module exactly once the declared rewrites are un-applied, and (b) never touch — not even adjacently — any node this repo's own `_claim_license_relevant_subtrees` function or a `*LICENSE*`-named module constant identifies as content.
4. **Sizing, sampled directly, not inherited:** four real surfaces sampled across the file-size distribution show 5.3%–11.1% of file LOC (mean ≈ 9%) is mechanically extractable once claim-license content and domain/posture logic are correctly excluded — see §3.4. Applied to the guard-protected set's 93,039 LOC, that is a **ceiling** of roughly 4,600–10,200 LOC if every protected module were eventually adopted family-by-family, consistent with (and independently arrived at, not copied from) the ~5–8k LOC estimate this spec was briefed against. Increment 1's actual, rule-registry-limited yield is far smaller: on the order of a few hundred LOC (§8). The 31k figure from the original audit overstates true extractable mass because it counts by function-*name* pattern, and roughly 4.8k of it is claim-license content the harness may never own regardless of mechanism.
5. **Sequencing:** adopt in place on the flat tree, not gated on packaging's P4 relocation (§10). Packaging P1 has landed (`plugins/setec-voiceprint/scripts/setec/` exists, all subpackages empty per their own docstrings); P2–P4 have not. The rule registry in §6 is written against the *current* flat-tree import shape; sequencing after P4 would require deriving a second, different rule registry for no proven benefit, since harness value is orthogonal to file location.
6. **Weakest point, stated plainly, not buried:** the guard amendment is more code than the guard has ever run before (`compare_protected_modules` today does one `ast.dump` equality check; the amendment adds transform application). More code executing inside a fail-closed gate is more surface for a subtle bug that manufactures a false pass. §6.6 names the mitigation (a golden-fixture suite is a merge-blocking part of the amendment itself, not an afterthought) and states directly why that mitigation is necessary rather than sufficient.

### 1.1 Existing regression coverage this spec must not contradict

`plugins/setec-voiceprint/scripts/tests/test_check_claim_license_guard.py` already pins the exact failure mode this spec's amendment must avoid reintroducing. `test_moves_substring_laundering_is_blocked`'s docstring records that an earlier revision of the guard's move-map handling did a raw `str.replace` on the whole `ast.dump()` **text** keyed by a committed `old_symbol`/`new_symbol` pair, and that `old_symbol="REPORTS"` / `new_symbol="REFUSES"` could silently invert a license sentence containing "REPORTS" as a substring while being "explained" by a bogus symbol-rename row. The fix — visible in the current `tools/check_claim_license_guard.py`, which no longer contains any `_normalized_dump` or text-substitution code path at all — was to make `load_move_map` reject any non-empty `moves`/`path_rewrites` outright at P1, deferring the entire question of *how* a legitimate structural delta gets authorized to whichever phase first needs one. That deferred question is what §6 answers. §6.2 explains, concretely, why the mechanism proposed there cannot repeat that failure.

## 2. Scope

**The harness owns**, for any surface that adopts it:

- Common CLI plumbing: `argparse.ArgumentParser` construction (`prog`/`description` passthrough) and exactly three shared flags — `--json`, `--out`, `--out-md`. Nothing else. Every domain-specific flag (`--judge`, `--cap-per-question`, `--function-top`, …) stays authored in the surface's own `build_arg_parser`.
- Envelope composition **shape**, via a thin, argument-identity-preserving passthrough to `output_schema.build_output` / `build_error_output`. The harness never constructs a `ClaimLicense` on a surface's behalf (§4).
- A markdown report **skeleton**: a title heading, a standard metadata line, and a claim-license-rendered footer. Sampling (§3.4) found these account for at most a handful of lines per surface (4–6 of `render_report`/`render_markdown`'s 40–61 lines in the sampled files) — the bulk of every report function sampled is surface-specific content shape (feature tables, pair listings, tallies) that the harness does not and should not templat.
- `_emit`: writing the JSON/markdown output to file and/or stdout. One canonical signature, replacing the four divergent ones observed in §1.

**The harness never owns, under any mechanism in this document, in any increment:** claim-license CONTENT. No harness-level default for `licenses`, `does_not_license`, or `comparison_set`. Every surface keeps its own license text verbatim, in its own module, and constructs its own `ClaimLicense(...)` (or `_claim_license*`-named function). This is not merely a style preference; §4 explains why it is a load-bearing compatibility requirement for the guard, not just an ethical one.

## 3. Sizing method and result

### 3.1 Why a name-pattern count overstates extraction

The original audit classified LOC as "boilerplate" by function name (`main`, `build_arg_parser`, `compose_envelope`/`render_report`, `_emit`/`_error_envelope`). Applying that same classification to `fallacy_scan.py` (433 LOC) captures 243 lines — 56% of the file — because it counts every line inside those six functions, including the parts of `compose_envelope` that build per-judge-kind caveats (posture-critical prose, not scaffolding) and the parts of `main` that implement the surface's own prompt-fingerprint drift gate (`_effective_judge_fingerprint`, entirely domain logic). Scaled across the codebase this produces something close to the ~31k / 15.8% figure. It is real code, but "matches a boilerplate-shaped function name" is not the same claim as "is mechanically extractable into a shared harness."

### 3.2 Method

Four real top-level surfaces were read in full and every line classified into exactly one of: (a) mechanically replaceable by a fixed, enumerable harness call with no change to any argument value, (b) domain or posture logic that must stay in the surface, or (c) claim-license content, which stays in the surface by design regardless of mechanism. Samples were chosen to span the file-size distribution (median top-level script size: 666 LOC; p25: 414; p75: 976) rather than cherry-picked:

| File | LOC | Chosen because |
|---|---:|---|
| `fallacy_scan.py` | 433 | named explicitly in this spec's brief as the prior reviewer's "59% overstates" example |
| `agd_move_scan.py` | 395 | near-clone of `fallacy_scan.py`'s family shape — a second, independent read of the same pattern |
| `voice_profile.py` | 433 | named explicitly in this spec's brief as "80% boilerplate" |
| `position_pair_register.py` | 666 | at the file-size median; carries a runtime posture gate (`_assert_no_banned_keys`) called from inside `compose_envelope`, so it stress-tests whether "envelope composition" can be genericized at all |

### 3.3 What each sample showed

- **`fallacy_scan.py`**: ≈48 of 433 lines (11.1%) extractable — the `sys.path` bootstrap, the `--json`/`--out`/`--out-md` flags and parser skeleton, `_emit`, `_error_envelope`, and the read-target/`OSError` guard in `main`. Everything else — the judge-kind caveat text in `compose_envelope`, all judge-specific `build_arg_parser` flags, `_effective_judge_fingerprint`'s manifest-vs-current-fingerprint precedence logic, `render_markdown`'s tally/flag-list rendering — is domain logic that does not generalize.
- **`agd_move_scan.py`**: ≈43 of 395 lines (10.9%) — same shape, independently confirming the family pattern rather than one file's idiosyncrasy.
- **`voice_profile.py`**: ≈23 of 433 lines (5.3%) — markedly *lower* than the file explicitly flagged as "80% boilerplate." This file inlines its argparse construction directly in `main()` (no separate `build_arg_parser`) and has no `_emit` at all — it hand-writes three separate privacy-guard-then-write blocks (`--json-out`, `--out`, stdout), a pattern that recurs in `pov_voice_profile.py` and `voice_drift_tracker.py` but not the other ~185 top-level scripts, so it is a *family*-specific duplication, not a harness-scope duplication. The "80%" figure most plausibly measures how much of the file is *not* the stylometric math (which lives in `stylometry_core.build_profile`, imported) rather than how much is harness-extractable; those are different claims, and only the second one is in scope here.
- **`position_pair_register.py`**: ≈51 of 666 lines (7.7%). This file is the clearest illustration of why "envelope composition" cannot be handed wholesale to a harness: `compose_envelope` calls `_assert_no_banned_keys(envelope)` — a runtime gate, unique to this surface, that raises before a relation/verdict key can escape in the envelope — immediately before returning. A harness that owned the return statement outright would either drop that call silently (a posture regression) or need a per-surface post-hook parameter, at which point "the harness owns envelope composition" has quietly become "the harness owns an outer wrapper around a surface-authored function," which is a much smaller claim.

**Mean across the four samples: 8.75%, call it 9%.** Range 5.3%–11.1%.

### 3.4 Reconciling with the ~5–8k LOC estimate this spec was briefed against

Applying the sampled 5%–11% range to the guard-protected set's 93,039 LOC gives **4,652–10,234 LOC**, centered at ≈8,374 LOC at the 9% mean — a ceiling on what mechanical extraction could ever remove if every one of the 110 protected modules were eventually adopted, family by family, across many future increments. This independently derived range brackets and is consistent with the ~5–8k LOC estimate this spec was briefed to check. It also explains, mechanically, why the ~31k figure is high: roughly 4.8k of it (§1) is claim-license content that no mechanism in this document may touch, and sampling shows the remainder is, on average, ≈91% domain or posture logic wearing a boilerplate-shaped function name. **This is a ceiling, not Increment 1's yield** — §8 shows the rule-registry-limited Increment 1 scope realistically extracts a few hundred LOC, because most of the 110 protected modules do not share an *exact* structural match with any single proposed rule (§1's four divergent `_emit` signatures are the clearest evidence of that).

## 4. The compatibility requirement that shapes everything else

The harness must never construct a `ClaimLicense` object, never supply a default `licenses`/`does_not_license` string, and never wrap the `ClaimLicense(...)` call site inside its own code. This is stated as scope in §2; here is why it is load-bearing rather than stylistic.

`check_claim_license_guard.build_protected_set()` seeds its protected set by a naming convention: any module whose AST defines a name matching `_claim_license*` or directly calls `ClaimLicense(...)`. If the harness *itself* constructed `ClaimLicense` objects on behalf of callers (e.g., a `harness.compose(licenses=..., does_not_license=..., ...)` helper that built the `ClaimLicense` internally), then every future surface's actual claim-license content would live inside a call to *harness* code, not inside the surface's own module — and the guard's naming-convention seed detection, which only scans plugin-runtime modules for their *own* `_claim_license*`/`ClaimLicense(...)` sites, would need to either (a) treat the harness module itself as one giant permanently-protected seed carrying every surface's content undifferentiated, which defeats per-surface change tracking entirely, or (b) be taught to trace content back through an indirection layer, which is exactly the kind of interprocedural dataflow analysis the guard's own docstring disclaims ("no claim of general semantic or interprocedural dataflow analysis... fails closed" on anything it cannot resolve to a unique source module).

The design adopted instead avoids the problem rather than solving it: **every surface — adopted or not, forward or legacy — keeps a literal `ClaimLicense(...)` call or `_claim_license*`-named function in its own module**, and passes the *already-constructed* `ClaimLicense` object into `harness.compose(...)` as a value. The guard's existing, unmodified seed-detection logic therefore continues to correctly seed every future surface exactly as it does today, with zero changes to that logic. This is also why the guard amendment in §6 never needs to reason about the harness module at all — the harness is not itself a supplier of license content by construction, so it cannot enter the protected closure and does not need its own carve-out.

## 5. The forward-only ratchet

A new checker — proposed name `check_new_surface_scaffolding`, modeled directly on the "new edges are errors, existing exceptional edges may only disappear" ratchet convention `specs/svp-packaging-conversion.md` describes for its own (not yet built) layering checker — computes the set of `.py` paths present in the candidate tree under `plugins/setec-voiceprint/scripts/` (top-level only) that are **absent from the merge-base tree** (`git diff --diff-filter=A` against `origin/main`, the same merge-base resolution `check_claim_license_guard.merge_base()` already performs). For each such new file that defines its own `TASK_SURFACE`:

- It must import the harness's `_emit`/`error_envelope`/`add_common_output_args` equivalents rather than defining its own module-level `def _emit(`, `def _error_envelope(`, or duplicating the three common flags inside its own `build_arg_parser`.
- A narrow, named exemption file (same shape as packaging's `packaging_migration_exemptions.yaml`: path, reason, owner, introduced SHA) is the only escape hatch, reviewed the same way a layering exemption is reviewed.

Because this checker only ever inspects paths that do not exist at the merge base, it **cannot** touch, re-derive, or interact with `build_protected_set()`'s closure computation in any way — a new file cannot retroactively be "already protected," and the ratchet's pass/fail has no bearing on the Deficit Lock. This is the cleanest possible relationship between two gates: total independence.

**Non-vacuity:** a fixture new top-level file that defines `TASK_SURFACE` and hand-rolls its own `_emit`/`build_arg_parser` must fail the ratchet; the same file rewritten to import the harness equivalents must pass. Both are cheap, deterministic, and require no git history beyond the merge-base diff already being computed.

## 6. The guard amendment

### 6.1 What the current guard proves, and what adoption needs it to keep proving

`compare_protected_modules` today does exactly one thing per protected module: `ast.dump(base, include_attributes=False) == ast.dump(candidate, include_attributes=False)`, whole-module, no exceptions, sourced from `git show <merge-base-sha>:<path>` on one side and the working tree on the other. `load_move_map` additionally requires `moves` and `path_rewrites` to be empty, unconditionally, at P1. Adoption needs *some* declared, bounded class of module deltas to stop being an automatic failure — while preserving, exactly, the property that a real content change is still caught with certainty, not probability.

### 6.2 Three shapes considered and rejected

1. **Owner sign-off in the PR body or a reviewed-artifact file that re-baselines a module's protected AST.** Rejected outright — the brief that authorized restoring this section is explicit that this is not a gate, and a re-baseline artifact is the same failure mode wearing a JSON extension: once a human (or a script trusting a human-authored file) can declare "this AST is now the new baseline," the guard's promise degrades from "provably unchanged since the merge base" to "unchanged since whenever someone last re-approved it," which is a materially weaker property with no mechanical way to tell the difference from the outside.
2. **A committed `old_symbol`/`new_symbol` (or `old_text`/`new_text`) substitution row, applied to the dumped AST text before comparison.** This is not a hypothetical risk — it is exactly the mechanism `test_moves_substring_laundering_is_blocked` (§1.1) documents as having been built, found exploitable, and removed from this exact file. A row that can rewrite text can rewrite text on both the base side and the candidate side identically, cancelling a real content delta; that is true regardless of how the row is named, scoped to "only scaffolding," or restricted in length. No shape in this family is proposed anywhere in this document.
3. **Scope comparison to only `_claim_license_relevant_subtrees()`'s output, ignoring the rest of the module.** Rejected because it is unsound, not merely weaker: `_claim_license_relevant_subtrees()` finds `ClaimLicense(...)` call sites and `_claim_license*`-named function bodies, but `fallacy_scan.py`'s and `agd_move_scan.py`'s actual license text lives in module-level `DEFAULT_LICENSES`/`DEFAULT_DOES_NOT_LICENSE` constants that reach the call site only through a CLI-default indirection (`p.add_argument("--licenses", default=DEFAULT_LICENSES)` → `args.licenses` → a function parameter → the `licenses=` keyword). The subtree detector, used alone, would not even see the constant's assignment statement, and a rule that "only touches things outside the subtree" would be free to edit exactly that constant. §1 measured this gap directly: 744 of the ≈4,800-line content estimate lives in exactly this indirection pattern, outside the subtree. This is why §6.4's exclusion zone below is the *union* of the subtree detector and every `*LICENSE*`-named module-level assignment, not the subtree detector alone.

### 6.3 The mechanism

**A closed, code-defined rule registry, never a data file.** A small, fixed set of named rewrite rules lives as Python (proposed home: a `RULES` structure inside `tools/check_claim_license_guard.py` itself, or a sibling module it imports), each entry specifying:

- a **matcher**: an exact AST shape (e.g., "a module-level statement pair matching `SCRIPT_DIR = Path(__file__).resolve().parent` followed by the `if str(SCRIPT_DIR) not in sys.path: sys.path.insert(...)` guard, verbatim"), never a fuzzy or partial match;
- an **expected cardinality**: how many times the matcher must fire in the base module (a rule that matches zero or an unexpected count is a hard failure, not a partial success);
- a **replacement**: a *fixed*, rule-defined statement or import (e.g., "delete the matched block; insert `from surface_harness import emit as _emit`") — never a statement synthesized from any value found in the diff.

Every rule falls into exactly one of two operation kinds, and a registry self-check (§6.7) enforces that no future rule addition falls outside them:

- **Deletion-with-fixed-insertion**: remove a matched statement or function body wholesale; insert a fixed, rule-authored replacement. Used for the `sys.path` bootstrap (rule **R1**), and for whole hand-rolled `_emit`/`_error_envelope` function bodies matched by name and the exact signature shape found in §1 (rules **R3**/**R4**, scoped to the 6-module judge-scan family in Increment 1).
- **Callee rename with mandatory argument-value identity**: rewrite `build_output(kw1=v1, kw2=v2, ...)` to `harness.compose(kw1=v1, kw2=v2, ...)` (rule **R5**) or `build_error_output(...)` to `harness.error_envelope(...)` (rule **R6**) or `argparse.ArgumentParser(description=..., prog=...)` to `harness.build_parser(description=..., prog=...)` (rule **R7**) **if and only if** every keyword name and every argument value sub-expression, compared as AST (`ast.dump`, not text), is identical between base and candidate. No rule renames a callee whose arguments differ in any way — a rule whose precondition fails simply does not apply, and an adoption that requires it fails closed.

None of R1/R3/R4/R5/R6/R7 ever inspects, reads, or is conditioned on a string *value* found anywhere in the diff. R2 (argparse common-flag extraction — deleting the `--json`/`--out`/`--out-md` `add_argument` calls in favor of `harness.add_common_output_args(p)`) is deliberately **not** included in Increment 1: its matcher would need to select specific `add_argument` calls by their first positional argument (a small, closed literal set — `"--json"`, `"--out"`, `"--out-md"` only, and *never* extensible to `"--licenses"`/`"--does-not-license"`, enforced by the same registry self-check), and getting that allowlist verifiably right against all 50 protected `build_arg_parser`-bearing modules is exactly the kind of per-family verification work Increment 1 defers (§8).

**Verification, per declared adoption:**

1. A new committed file, `harness_adoption_registrations.json`, schema-mirrored on `packaging_move_map.json`: `{"schema": 1, "adoptions": [{"path": "...", "rule_ids": ["R1", "R5", ...]}]}`. This file is PR-writable — and that is fine, because it authorizes nothing by itself. It only tells the guard which rules to *attempt*; every rule's own precondition (matcher, cardinality, argument-identity) is independently re-checked by CI on every run, against the merge base fetched fresh via `git show`, never against a snapshot the registration file could itself misrepresent. A wrong or malicious row (naming a rule that does not structurally apply) fails the run — it cannot cause one to spuriously pass.
2. For each registered `(path, rule_ids)`: fetch the base module fresh (`build_protected_set_at_revision`'s existing machinery). Apply each declared rule **forward from the base AST** (never by reverse-engineering the candidate) to produce an expected-candidate AST. Require `ast.dump(expected_candidate, include_attributes=False) == ast.dump(actual_candidate, include_attributes=False)` exactly. This is the same whole-module equality assertion the guard already makes today, generalized only by "expected" now meaning "base plus exactly the declared, pinned transforms" instead of "byte-identical to base."
3. **Independently**, and regardless of which rules are declared: compute the exclusion zone — the union of `_claim_license_relevant_subtrees()`'s spans and every module-level `*LICENSE*`-named assignment's span (§6.2, item 3) — on both base and candidate. Require the set of spans to be positionally and structurally identical (`ast.dump` per span) between base and candidate, **and** require that no rule's matched region overlaps any exclusion-zone span in either the base or candidate AST. This is deliberately redundant with step 2: step 2 alone would already catch a content change (the whole-module reconstruction would fail to match), but a second, independent, narrower assertion pinned specifically to "the license-bearing nodes did not move and did not change" gives a review-legible failure message ("claim-license content changed at `<path>`") instead of a generic "reconstruction mismatch," and survives a hypothetical bug in one check without depending on the other.
4. Any ambiguity — a declared rule whose cardinality does not match, a reconstruction that does not equal the candidate exactly, an exclusion-zone span that shifted or changed — is a hard failure (`GuardError`, exit 2), matching the existing guard's fail-closed posture for star imports and unresolved provenance.
5. A protected module **not** listed in `harness_adoption_registrations.json` is checked exactly as today: whole-module identity against the merge base, zero tolerance, zero rule application. Adoption is opt-in per file; nothing about this amendment relaxes the default.

### 6.4 Why this cannot repeat the §6.2 failure

Every rule in §6.3 is a *deletion-of-a-fixed-pattern-with-fixed-insertion*, or a *rename requiring full argument-value identity*. Neither operation kind can take a string value found in the diff and place it anywhere — there is no code path in this design that reads a `Constant` string node's `.value` and writes it back out transformed. A rule attempting to touch a `*LICENSE*`-named assignment or the `ClaimLicense(...)` call's keyword arguments would need either (a) to be a deletion rule matching that exact statement, which the exclusion-zone disjointness check in step 3 refuses outright regardless of what the rule's author intended, or (b) to be a rename rule, which by construction only fires when the argument values are *already* identical — meaning it is structurally incapable of being the vehicle for a content change even in principle, independent of the exclusion zone check.

### 6.5 The honest limit of the exclusion zone

`_claim_license_relevant_subtrees()` plus `*LICENSE*`-named assignments is a **lower bound** on content, established empirically in §1 (the 744-line gap). It is possible, though no example was found in the four sampled files or in a broader `LICENSE`-name scan across all 110 protected modules, that some surface threads license-adjacent text through a name that does not contain "LICENSE" and is not one of the `_claim_license*` seed shapes. §6.3 step 2's whole-module reconstruction equality is the actual backstop against that case — it does not depend on the exclusion zone being complete, because it requires the *entire* module (not just the flagged zone) to reconstruct exactly. The exclusion zone exists for a legible failure message and defense in depth, not as the primary guarantee.

### 6.6 The weakest point, and its mitigation

This amendment asks the guard to do more than compare two strings for equality: it applies rule transforms to an AST and compares the result. That is meaningfully more code executing inside a gate whose entire value proposition, to date, has been its simplicity — `ast.dump(a) == ast.dump(b)` is close to unarguable; a transform-then-compare pipeline is not. A subtle bug in rule application (an off-by-one in which statement a matcher selects, an incorrect assumption about statement ordering, a cardinality miscount) could, in the worst case, manufacture a false equality where none exists — precisely the failure class `test_moves_substring_laundering_is_blocked` pins a *different* instance of. The mitigation proposed here is procedural, not a claim that the risk is eliminated: the amendment itself, as a merge-blocking condition, ships a golden-fixture suite in the same idiom as `test_check_claim_license_guard.py`'s existing `fake_repo` fixture (§1.1) — at minimum, one fixture per rule proving a legitimate application passes, one fixture per rule proving a cardinality mismatch fails closed, and the two fixtures specified in §6.8 proving content-laundering attempts fail. This raises confidence; it does not convert "more code" into "no more risk than before," and this document does not claim otherwise.

### 6.7 Rule registry governance

Adding a rule to the registry is a code change to `tools/check_claim_license_guard.py` (or its sibling), reviewed at the same bar as this spec, never a data-file edit. A static self-check enumerates every registry entry's operation kind at CI time and fails if a future entry is neither "deletion-with-fixed-insertion" nor "rename-with-mandatory-argument-identity" — closing off, mechanically, any future attempt to reintroduce a value-parameterized rule under a new name.

### 6.8 Non-vacuity tests (the demanded proof that the gate can fail)

Modeled directly on `test_check_claim_license_guard.py`'s `fake_repo` fixture idiom (§1.1):

1. **Legitimate adoption passes.** A `fake_repo` module built from `fallacy_scan.py`'s real `sys.path` bootstrap plus `_emit` shape, registered with `rule_ids: ["R1", "R3"]`, transformed exactly as R1/R3 specify → `clg.run()` passes.
2. **The demanded planted-softening fixture.** The same base module, but the candidate's `ClaimLicense(...)` call has one word changed in `does_not_license` (e.g., "does NOT license" → "does license"), while the rest of the file is transformed exactly per R1/R3 and registered accordingly → `clg.run()` must fail, and the failure must be attributable: either R5/R6 is not declared (so the module falls back to full whole-module comparison, which fails on the changed keyword value) or, if R5 is declared, its argument-identity precondition fails outright (the `does_not_license` sub-expression differs), so the rule cannot apply and the run fails closed rather than silently proceeding. Both paths must be exercised as separate fixtures.
3. **Cardinality mismatch fails closed.** A registration declares `R1` for a module whose `sys.path` block does not exactly match R1's pattern (e.g., an extra blank line breaking the exact statement-pair match, or the block appearing twice) → `GuardError`, not a silent skip.
4. **Exclusion-zone disjointness catches an out-of-band edit.** A registration declares only `R1`, but the candidate also has an unrelated one-word edit inside a `*LICENSE*`-named constant elsewhere in the same file → fails, because the exclusion-zone span set differs between base and candidate independent of any rule application.
5. **Ratchet non-vacuity** (§5): a new top-level file defining `TASK_SURFACE` with a hand-rolled `_emit` fails `check_new_surface_scaffolding`; the same file importing the harness's `emit` passes.

## 7. Optional adoption outside the protected closure

The 4 modules identified in §1 (`setec_run_set.py`, `restoration_packet.py`, `before_after_restoration.py`, `diveye_signals.py`) may adopt the harness with **zero interaction with the guard mechanism in §6** — they are, by the guard's own oracle, outside the protected closure, so ordinary code review is the only gate. This is worth doing precisely because it is free, not because the yield is large: at the sampled 5%–11% rate, 4,255 LOC yields roughly 210–470 lines. The remaining 26 of the original 30 candidates should **not** be pushed into this harness at all — they do not call `build_output`/`build_error_output`, and forcing an envelope-shaped harness onto acquisition scripts that were never shaped like a capability surface is scope creep this spec explicitly declines.

## 8. Increment 1 boundary

**In:**

- The forward-only ratchet (§5), unconditionally — it has no guard dependency and no sizing risk.
- The harness module providing `add_common_output_args`, `build_parser`, `emit`, `error_envelope`, `compose` (thin `build_output` passthrough), `report_header` (the title/metadata/footer skeleton from §2).
- The guard amendment mechanism (§6.3) and rules **R1** (sys.path bootstrap — safe against all 75 matching protected modules; the least content-adjacent rule in the registry) and **R3/R4/R5/R6** (`_emit`/`_error_envelope`/`build_output`-rename/`build_error_output`-rename), applied **only** to the 6-module judge-scan family identified in §1 as sharing an exact `_emit` signature — this is the proof-of-mechanism increment, not a blanket authorization.
- Optional adoption of the 4 unprotected envelope-shaped modules (§7).
- The full non-vacuity fixture suite (§6.8, §5).

**Deferred, explicitly, not silently:**

- Rule **R2** (argparse common-flag extraction) — needs a verified, closed allowlist audit against all 50 `build_arg_parser`-bearing protected modules before it is safe to enable broadly; Increment 1 does not attempt it.
- Adoption of any protected module outside the 6-module judge-scan family — each additional family (e.g., the `(envelope, args, *, as_markdown)` `_emit` shape shared by `position_pair_register.py`, `compression_edit_distance_audit.py`, `tocsin_audit.py`, `rank_space_audit.py`, `gecscore_audit.py`, `cross_doc_argument_consistency.py`) needs its own reviewed rule addition per §6.7, not a copy-paste of R1–R7.
- `packaging_move_map.json`/`harness_adoption_registrations.json` interaction if packaging P4 relocation ever proceeds concurrently — out of scope for this document; see §9 for why it is not expected to be necessary.
- Any change to `output_schema.py`, `claim_license.py`, or the `ClaimLicense` constructor signature itself. This spec designs the *mechanism* that would let a future breaking contract change fan out safely; it does not propose that change.

## 9. Sequencing: in place, not after relocation

Adopt in place on the current flat tree. Three reasons, none of them merely "packaging said so" (packaging's own §3 explicitly disclaims authority over this question — it withdrew the harness from *its* scope, it did not mandate an order for a future harness spec):

1. **Each file is touched once.** If adoption instead waited for packaging's P4 (family-by-family relocation, ~10 PRs by that spec's own phase count), every adopted module would be edited twice — once for the physical move, once for harness adoption — doubling guard interaction and review surface for no benefit.
2. **The rule registry in §6.3 is written against today's import shape** (`from claim_license import ClaimLicense`, the flat `sys.path` bootstrap R1 targets). P2's relocation of `claim_license.py`/`output_schema.py` behind compatibility launchers, and P4's eventual package-relative imports, would change the exact statements R1/R5/R6/R7 match — a second registry would need to be designed and re-reviewed for the post-relocation shape, duplicating §6's review cost for zero additional capability.
3. **Harness value is orthogonal to physical file location.** A shared `_emit`/argparse/envelope helper works identically whether the caller lives at `plugins/setec-voiceprint/scripts/fallacy_scan.py` today or at a P4-relocated path inside `setec.surfaces` later. There is no technical dependency running from harness adoption to relocation in either direction — and adoption may, incidentally, make P4 *easier* later: post-adoption modules converge on a smaller set of `(has_main, has_TASK_SURFACE)`-adjacent shapes, which is exactly what packaging's launcher-template classification (§2 of `specs/svp-packaging-conversion.md`) already keys off.

This does not argue the ~10-PR P4 tail is unnecessary — packaging's stated motivations for it (zero-install layering, `sys.path` hygiene) are independent of this spec's LOC concerns — only that nothing about *this* spec should be gated on it, and that doing this work first does not foreclose or complicate P4 landing afterward.

## 10. Acceptance gates (computable predicates)

1. `check_new_surface_scaffolding` (§5) exits non-zero on any new top-level `.py` file (absent from the merge base) that defines `TASK_SURFACE` and hand-rolls `_emit`/`_error_envelope`/the three common flags, with no unlisted-exemption escape.
2. The amended `check_claim_license_guard.py`: every module in `harness_adoption_registrations.json` passes the forward-transform-then-whole-module-equality check (§6.3 step 2) **and** the independent exclusion-zone identity check (§6.3 step 3); every protected module *not* listed continues to require exact whole-module identity, unchanged from today.
3. Every rule in the registry is classified by the self-check (§6.7) as exactly one of the two closed operation kinds; CI fails if a new entry is neither.
4. All five §6.8 fixtures and the §5 ratchet fixture pass, including the two that assert the gate **fails** (planted softening; cardinality mismatch) — a suite with zero failing-case assertions is rejected as non-vacuous-incomplete per this repo's own recurring finding about gates that cannot fail.
5. `packaging_move_map.json` and `harness_adoption_registrations.json` are validated independently; neither schema references or depends on the other.
6. Existing `tools/check_claim_license_guard.py` tests (`test_check_claim_license_guard.py`, currently 496 lines / dozens of cases per §1.1) continue to pass unmodified — the amendment is additive to the module's public surface, not a rewrite of `compare_protected_modules`'s default (unregistered) code path.
7. `python3 tools/spec_anchor_lint.py --spec specs/svp-surface-harness.md --repo .` returns zero HIGH-confidence gating findings.
8. `python3 tools/check_docs_freshness.py` passes (this spec introduces no `capabilities.d` entry, so the CHANGELOG-coverage check is unaffected by construction).

## 11. Out of scope

- Any change to `output_schema.py`, `claim_license.py`, `ClaimLicense`'s constructor, or `capabilities.py` — the L0 contract modules stay exactly as they are.
- Rule R2 and any protected-module family beyond the 6-module judge-scan set — future increments, each its own reviewed addition per §6.7.
- The 26 acquisition/utility modules outside the protected closure that do not build an envelope (§1, §7) — not a harness target regardless of guard status.
- Packaging's P2–P5 (`specs/svp-packaging-conversion.md`) — untouched, unblocked, and not a prerequisite (§9).
- A wheel/distribution build, `pip install`, or any packaging-format change — inherited as out of scope from the packaging spec and not reopened here.
- Retroactively re-scoping any already-shipped capability's `ClaimLicense` content "while we're in the file" — adoption under this spec is scaffolding-only by construction (§6.4); a genuine content change to any surface remains its own, separately reviewed PR, exactly as `specs/svp-packaging-conversion.md` already establishes for packaging moves.
